Architecture walkthrough

Decision models
& Clef-Flash

This guide explains how a pretrained language model can make decisions by scoring supplied options instead of generating answer text.

Part I builds a simple decision-model blueprint: pack the state, question, and candidates; extract their representations; learn to compare them; and examine training and choice-order effects.

Part II describes Cloudflare's Clef-Flash implementation. Its joint schema head keeps token evidence available, lets options read that evidence, and lets related questions interact before returning typed answers.

TL;DR

  1. Reuse pretrained language representations. The transformer turns the request and candidate descriptions into contextual vectors.
  2. Learn a shared comparison rule. A decision head produces one score per supplied candidate. Softmax converts the scores into probabilities. The output is indexed by the request’s choices rather than the LLM’s vocabulary.
  3. In Clef-Flash, keep the evidence accessible. Options read token-level evidence, and related questions exchange information before their options are scored.

Before the architecture / Question types

Three ways to interpret option probabilities

A conventional sentiment classifier has a fixed output space: positive, negative, and neutral. The developer knows those labels before training and can build a three-output classification head. A general-purpose decision model instead receives the question and its candidate descriptions with each request. Today it might choose a support team; tomorrow it might compare refund reasons. Its shared scorer operates on candidate representations rather than a permanently assigned set of class outputs.

“Universal” describes that flexible contract, not unlimited capacity or guaranteed generalization. Candidate descriptions can be detailed and candidate counts can vary, subject to context, compute, and serving limits. Within that contract, choice, noul, and score are closely related architecturally:

Choose among alternatives

choice

Which team should handle the duplicate-charge request?

  • Billing
  • Technical support
  • Account access

Readout: probabilities over the supplied teams; return the highest-probability team when a single choice is needed.

Evaluate a proposition

noul · boolean

Is the customer asking for a refund?

  • True / Yes
  • False / No

Readout: a two-choice distribution, summarized by the probability of True. This is a Bernoulli outcome, not a “null,” missing-value, or abstention response.

Locate an answer on a scale

score

How urgent is the request?

  1. 0 Routine
  2. 1 Soon
  3. 2 Immediate

Readout: probabilities over ordered levels, mapped to a numeric summary such as their probability-weighted average. Preserve the level order and declared numeric spacing.

The architectural common ground

Encode the state, question, and options → score valid options → normalize their scores. Boolean questions supply two options; score questions supply ordered levels. Task conditioning, training targets, and final post-processing can differ without requiring three fundamentally different backbones.

We therefore develop the choice path first. It exposes the shared machinery; noul and score reuse it with different option semantics and readout rules. The terminology comes from the supplied material; this guide uses the local API’s spelling noul for the boolean mode. Part II shows its concrete typed readouts.

Schema-bound does not mean always correct. Restricting answers to supplied options is not a general “no hallucination” guarantee. The precise architectural guarantee is narrower: the choice readout cannot invent an out-of-schema label. It can still select the wrong team, report an overconfident probability, or miss the correct answer because that answer was never supplied.

01 / Describe the decision

Give the model the whole decision

Start by separating the facts from the decision. The state is the customer’s message. The question asks which team should handle it. The candidates describe the available teams. The same state could support a different question—such as whether the customer needs a refund—so the question is part of the input, too.

For this blueprint, we serialize the question, state, and K candidate descriptions together. This is a joint encoder: the transformer processes the situation and choices within the same sequence. We finish with a fixed suffix, The answer is:. Despite its wording, this suffix is not an invitation to generate text. It gives us a consistent location from which to read a hidden state.

During training, the record also carries the correct candidate’s index, y. For our example, that index points to Billing. Keeping the label outside the sequence is essential: the model must learn to make the decision, not read the answer out of its input.

Implementation note: preserve token boundaries

The tokenizer turns this text into N tokens. Record the index of each candidate’s last content token and the final non-padding token. Use token spans or tokenizer offsets so that punctuation, separators, and subword tokenization are handled consistently.

\[\begin{aligned} \texttt{input\_ids} &: [B,N] \\ \texttt{choice\_end} &: [B,K] \\ \texttt{answer\_end} &: [B] \end{aligned}\]

B = batch size; N and K can be padded batch dimensions. Keep token and candidate masks. Preserve all candidate boundaries and the suffix when applying a context-length budget.

02 / Reuse the representations

Language knowledge becomes decision evidence

An LLM does more than produce vocabulary probabilities. Before its language-model head predicts a token, the transformer has built a hidden state at every input position: a vector of width d that represents that token in context. These are the features we want to reuse.

Pass our packed sequence through the pretrained backbone and take its final hidden states, rather than its next-token logits. We then select one vector for each candidate and one shared vector after all the candidates. For the triage example, a long token sequence becomes just four vectors.

The candidate vector \(c_i = H[\operatorname{end}(C_i)]\) comes from the last content token of candidate i. With full causal attention, it has access to that candidate’s text and everything before it. The answer vector \(a = H[\text{last non-padding token}]\) comes from the final suffix token, which has access to the question, state, and all the choices.

“Answer vector” names its role in our architecture; it is not an answer the LLM has generated. The suffix makes a convenient readout location, but pretraining does not guarantee that this state is already a good summary for our task. The decision objective will teach the trainable parts of the model how to use it.

The head receives K + 1 vectors, each of width d. Endpoint gathering is a simple readout strategy; span pooling or a learned pooling operation are other design choices.

How can a causal LLM process this in one forward pass?

Every input token is already known. A transformer can process the supplied sequence in one forward evaluation while a causal attention mask restricts each position to its prefix. Layers still execute in sequence; there is no loop that generates an answer token and feeds it back into the model.

Call the backbone’s hidden-state forward path and pass the selected vectors to the decision head. Computing next-token vocabulary logits is unnecessary for this readout.

Causal versus bidirectional attention

Causal: a candidate can see earlier candidates but not later ones. The final suffix can see all candidates. Bidirectional: candidate tokens can attend in both directions, subject to masking and context limits.

Both support this readout pattern. Retain the pretrained backbone’s attention behavior for a straightforward baseline; changing its mask is an architectural adaptation that needs training and evaluation.

03 / Learn to compare

From a few vectors to a choice

We now have representations of the decision and its choices, but not yet a rule for selecting a team. The head supplies that rule. It applies the same scoring function to each pair \((a,c_i)\), producing one scalar score, or logit, per candidate.

There are several ways to build this comparison. We can start with a dot product, make the comparison itself learnable, then let the vectors exchange information before scoring. Each step adds flexibility; none guarantees an improvement without training and evaluation.

Start with a dot product

Reuse the answer vector a for every candidate. Multiply each of its dimensions by the matching dimension of cᵢ, then add those products into a single score. All candidate scores can be computed together as a matrix–vector product.

A bare dot product has no trainable parameters. If we use it as our head, learning must happen in the backbone or in added projections. We cannot assume that pretrained hidden states already align in the way the routing task needs.

Make the comparison learnable

A dot product pairs matching dimensions. A bilinear layer inserts a learned matrix W, so any answer dimension can interact with any choice dimension. Each pair contributes a weighted product; summing those contributions gives one candidate score.

Now the head has something to learn even if the backbone is frozen. Diagonal weights reweight matching features; off-diagonal weights connect different features. Setting \(W = I\) recovers the dot product.

Crucially, W has \(d\times d\) weights, not one column per team. It acts on feature dimensions and is shared by all candidates. We can compute \(u = W^\top a\) once, then score every candidate with \(s = Cu\). A smaller projected width or low-rank W can reduce the cost when d is large.

Let the choices interact before scoring

Bilinear scoring compares each candidate with the shared answer vector. A more expressive head first lets the gathered vectors exchange information through two self-attention layers, then scores the refined pairs. In our example, the head can compare Billing with the alternatives, rather than evaluating each gathered candidate vector in isolation.

This is attention over a short list of vectors, not another pass over the original text. We couls also add a learned answer-role embedding \(e_a\) to distinguish the answer row from candidate rows. An optional task vector \(t\) can condition the head on the type of decision being requested.

Rows in X are vectors, not the original text tokens. Omit t for a head without task conditioning, giving K + 1 rows. The task output t′ supplies no candidate logit. Any projection into a smaller head width must also align the task and identifier embeddings to that width.

The backbone and head now contextualize at two different scales: the backbone works over text tokens; the head works over decision evidence. Full attention in the head lets a candidate use information from every other valid row, even when the backbone is causal. Padded candidate rows must be masked so they cannot influence that exchange.

Optional conditioning: task mode versus answer role

The source illustrates task modes named choice, null, and score. The task vector t is selected for a mode and enters attention as its own row. The answer-role embedding eₐ is instead added elementwise to a. These are two different signals, and neither adds a candidate logit.

This section follows only the single-choice probability path. Adding a task vector does not, by itself, define abstention or scoring behavior; those need their own output rules and training objectives.

Turn the scores into a distribution

Whichever head we use, its last step is the same: normalize the logits over the supplied candidates. For a single-choice decision, we return the candidate with the highest probability, along with the distribution if the application needs it.

NORMALIZE ACROSS VALID CHOICES
\[p_i = \frac{\exp(s_i)}{\sum_{j=1}^{K}\exp(s_j)}\]

The shared scorer is what makes the output space flexible. A request with three teams produces three logits; a request with five produces five. Unlike a fixed-label classifier with one learned output weight per class, this head scores the representations of the candidates supplied at runtime. Whether it generalizes to unfamiliar candidates still depends on the data and training.

There is one important limit to this contract: the model cannot select an answer missing from the candidate set. For support routing, the application supplies the team list. For extraction or search, a separate retrieval or candidate-generation step may be needed.

Engineering notes: candidate capacity, padding, and masked softmax

How many choices can one request contain?

The number of candidates K can vary between requests. A deployment may set a maximum K_max to bound request size and processing cost. Think of this as a row of choice slots, with each supplied candidate occupying one slot.

THE LIMIT QUOTED IN THE SCREENSHOT

At most 255 options

The Typesafe AI documentation excerpt shown in the screenshot states that a Choice question allows at most 255 options. This is a product limit quoted by the supplied material, rather than a universal limit of decision models.

For this blueprint, W ∈ ℝd × d acts on vector features and is reused for every candidate. A candidate-count cap does not determine its number of columns. Context length, memory, latency, and serving policy determine practical limits.

BEFORE THE DECISION MODEL

Supply the candidate set

The model selects among the candidates you provide. For extraction tasks, the screenshot suggests pattern matching for structured strings such as emails, phone numbers, or amounts; names may come from a known roster, a named-entity recognizer, or an LLM that proposes candidates.

Candidate generation determines what the decision model can select. Evaluate whether the desired answer reaches the candidate set as well as how accurately the head ranks it.

WHEN THE CANDIDATE SET IS TOO LARGE

Narrow the decision in stages: choose a section first, then choose a span inside it, as suggested in the screenshot. For other tasks, retrieve or shortlist candidates before scoring. Keep candidate identities through each stage and evaluate the full pipeline, since early filtering can remove the correct answer.

Mask unused scores before softmax

Suppose a fixed-capacity implementation reserves 255 slots and a request supplies 32 candidates. That leaves 223 padded slots. Replace their logits with −∞ before normalizing: they then contribute zero probability, and the probabilities of the 32 supplied candidates sum to one.

\[\begin{aligned} \tilde{s}_i &= \begin{cases} s_i & \text{if candidate } i \text{ is valid}, \\ -\infty & \text{otherwise} \end{cases} \\ p_i &= \frac{\exp(\tilde{s}_i)}{\sum_j \exp(\tilde{s}_j)},\qquad \sum_{i\,\text{valid}}p_i = 1 \end{aligned}\]
A COMPLETE NUMERICAL EXAMPLE

Five valid choices, then padding

To make the screenshot’s visible scores fully calculable, consider a separate request with exactly five valid candidates:

\[s = \begin{bmatrix}2.1 \\ 0.4 \\ -0.3 \\ 1.2 \\ -1.0\end{bmatrix},\qquad p \approx \begin{bmatrix}0.5797 \\ 0.1059 \\ 0.0526 \\ 0.2357 \\ 0.0261\end{bmatrix}\]

Any padded slots receive \(-\infty\) logits and zero probability. The five probabilities sum to one, up to rounding.

The source displays 32 choices with omitted scores, so its five displayed probabilities cannot specify that full distribution. Here all five valid scores are explicit.

MASK AT THE RIGHT STAGE

Exclude padding from normalization

A zero logit still contributes exp(0) = 1 to the denominator. Setting padded logits to −∞ removes that contribution. Zeroing probabilities only after softmax would leave the valid probabilities summing to less than one unless renormalized.

Use a numerically stable softmax and require at least one valid candidate per example. Mask padded candidates in the refinement attention too, so they cannot influence valid representations before scoring.

04 / Make choice order irrelevant

Should moving Billing change the answer?

Intuitively, listing Billing first or last should not change how well it fits a duplicate-charge request. But our packed sequence does not guarantee this. Moving a candidate changes its position and, in a causal backbone, which other candidates precede it.

THE DESIRED PROPERTY

Reordering candidates should reorder the probability vector in exactly the same way. After matching by candidate identity, the probabilities should stay the same. This is permutation equivariance of the candidate outputs.

A shared scorer and position-free self-attention over candidate vectors can be permutation-equivariant given the same candidate representations. The packed backbone may already have introduced order effects, so the head alone cannot guarantee the property for the full model.

The second transcript develops a structural solution for a full-attention causal backbone: give every candidate the same positional starting point, and prevent candidates from reading one another inside the backbone. The final answer suffix can still read the whole problem. Here the shared prefix includes question + state + prompt, extending the transcript’s shorthand “question” to our packed input.

First, give each choice its own local positions

With ordinary positions, a choice’s position IDs depend on the lengths of all preceding choices. Moving Billing from first to last changes both its physical location and its positional signal. Instead, keep the prefix positions and restart each choice at the first position after that prefix. Preserve the order of tokens within each choice.

\[\begin{aligned} \operatorname{pos}(P_r)&=r,\\ \operatorname{pos}(C_{i,r})&=L_P+r,\\ \operatorname{pos}(A_r)&=L_P+\max_i L_i+r. \end{aligned}\]

Here P is the shared prefix, A is the fixed answer suffix, Lᵢ is the length of a complete choice block, and r is a zero-based offset inside a block. In this schematic example, Technical support is the longest choice: 7 prefix tokens + max(4, 7, 5) choice tokens = position 14. The suffix’s second token uses position 15. Moving Billing to the end of the list keeps its IDs at 7–10 and the suffix at 14–15, because the maximum length stays the same. Continuing from whichever choice happens to be last would lose that property.

Position IDs are not always added embeddings. Learned absolute encodings can be added to token vectors. RoPE instead uses positions to rotate attention queries and keys. The reset rule concerns the positional signal supplied to the backbone; it does not change the physical token indices used to gather endpoints or build the mask.

Then, give every choice the same access to context

Resetting positions alone leaves a second asymmetry. Ordinary causal attention lets a later candidate read earlier candidates. In our running order, Billing reads the shared prefix and its own tokens; Technical support can also read Billing; Account access can read both earlier choices. Their available context depends on where they sit in the list.

For example, moving Technical support before Billing removes its access to Billing and gives Billing access to Technical support instead. Even with reset position IDs, this changes the information available to their hidden states. Positional resets alone therefore cannot guarantee choice-order equivariance.

To remove that asymmetry, treat attention as a directed visibility graph and remove the cross-choice edges: prefix tokens read their own past; each choice reads the entire prefix and its own past; suffix tokens read the prefix, all choices, and their own past. “Past” includes the current token in each causal block.

Read the removed regions by row: C₂ loses access to C₁; C₃ loses access to C₁ and C₂. C₁ already had no earlier choices to read. The two suffix rows remain causal: the first suffix token sees all candidates and itself, while the second also sees the first suffix token. Every retained connection stays on or below the physical token diagonal, even though the position IDs restart for each choice.

Why the full decision can now be equivariant

With unchanged candidate tokenization, local positions, and this mask at every backbone layer, each choice reads the same prefix and its own content in every ordering. Its hidden states therefore follow its identity through the permutation. The suffix has unchanged positions and attends to the same collection of keys and values; permuting that collection together leaves its attention result unchanged in exact arithmetic.

The head must preserve this symmetry too. Use shared scoring weights and refinement attention without candidate-rank embeddings or order-dependent masks. A fixed answer-role embedding and a task embedding independent of choice order are compatible. Candidate interactions can then happen in the symmetric head even though the backbone isolated the choice blocks.

\[C(\pi x)=\Pi C(x),\qquad a(\pi x)=a(x),\qquad p(\pi x)=\Pi p(x).\]

Here \(\pi x\) permutes whole candidate blocks and \(\Pi\) applies the same permutation to candidate rows. This is a structural property under those assumptions, rather than something established by shuffled training data. In evaluation mode, allow small numerical differences from floating-point reductions. Exact score ties also need an order-independent tie-breaking rule if the returned candidate identity must be stable.

When the construction applies

Full-attention causal backbones: the custom mask removes edges from ordinary causal attention. It retains backward-only visibility but changes the context and positional distribution, so fine-tune and evaluate the adapted architecture.

Bidirectional backbones: fully connected attention already treats candidate permutations symmetrically if positions, formatting, and all other biases also transform consistently. Resetting candidate positions addresses the positional part; a sliding window or order-dependent bias introduces additional constraints.

Hybrid, sparse, or recurrent attention: a custom dense mask may not control every information path. Window boundaries and recurrent state can still leak physical order. Check the actual layer implementation; the concrete hybrid backbone in Part II needs separate analysis before claiming this guarantee.

Ordered tasks: preserve order within each choice and within the state. This construction targets unordered alternative sets, including yes/no alternatives. If rank or sequence is part of a task’s meaning, retain that semantic information explicitly rather than erasing it indiscriminately.

For a score, preserve the scale’s meaning

The construction above targets unordered alternatives. A rating scale has semantic order: “terrible” is below “bad,” and “good” is below “great.” The source’s review example makes this distinction concrete. When the supplied list defines the scale from low to high, shuffling it changes the task’s definition.

There are two distinct contracts. If list position defines the numeric value, keep the levels in their declared order. If each candidate instead carries an explicit, stable value \(v_i\), a permutation-equivariant model can move the value and its probability together and preserve the expected rating:

\[\hat r = \sum_i v_i p_i,\qquad \sum_i (\Pi v)_i (\Pi p)_i = \sum_i v_i p_i.\]

This requires preserving the value–label mapping through packing and readout; it does not follow from resetting positions alone. The source’s 1–5 scale also assumes a numeric spacing when summarized by an expectation. Ordinal labels by themselves specify rank, not equal distances between levels.

The TypeSafe Score contract The TypeSafe API defines each level’s numeric value as its position in the supplied criteria array, starting at zero. Reordering urgency levels therefore reassigns their numeric meaning, even if their probabilities could otherwise be remapped by identity. Clef-Flash’s score readout follows this convention; it is an API contract, not a requirement of the joint schema head.

The model chooses within the world we give it

Two other boundaries are worth keeping in view. If Billing is absent, this single-choice head still distributes probability over the remaining teams; it has no built-in “none of the above.” And even when Billing is present, 0.72 is a model output, not a guarantee of correctness. Candidate coverage, an explicit abstention policy where needed, and confidence evaluation are parts of the system design.

The idea to carry forward

A decision model reuses an LLM’s language representations, then learns a different readout: compare the available choices instead of continuing the text.

05 / Train for decisions

Teach the readout what “correct” means

The architecture tells us where the scores come from. Training tells it which scores should be high. Each record contains (state, question, candidates, y), with one correct candidate index. We minimize cross-entropy over the candidate logits:

\[\mathcal{L} = -\log p_y = -s_y + \log\sum_{j=1}^{K}\exp(s_j)\]

For the duplicate-charge request, y points to Billing. If the head assigned Billing the illustrative probability 0.72, the loss would be about 0.329. The objective favors assigning more probability to Billing relative to the distractors. Across many labeled requests, this teaches a decision rule rather than a text-completion format.

A useful baseline is to freeze the backbone and train a newly initialized bilinear or attention-refined head. That tests how much the existing representations already support the task. If they need to adapt, train adapters or fine-tune the backbone alongside the head. Gradients flow only through the components we choose to update.

The candidate sets matter as much as the labels. Easy distractors can make the task look solved while teaching little about ambiguous requests. Evaluate on held-out examples with plausible alternatives, different candidate counts, and shuffled orders. Measure accuracy and log loss, but also calibration and end-to-end latency: a normalized probability vector is not automatically reliable confidence.

We now have the building blocks: a packed decision, selected hidden states, a shared scorer, and a supervised objective. But the blueprint is a starting point, not a claim that every decision model uses these exact components. Next, we will follow a concrete implementation that keeps the same output contract while making the readout substantially richer.

Part II / Inside Clef-Flash

What if a few gathered vectors are not enough?

Clef-Flash does not just compare candidate endpoints. It keeps token-level evidence available to the head, lets each option read that evidence, and lets several questions about the same state interact before returning their answers.

In the first part, the head received a deliberately small bottleneck: one vector per candidate and one answer vector. Once those were gathered, the head could refine them, but it could not go back to the rest of the sequence. A longer customer message might contain several separate facts, with different facts relevant to different decisions.

Clef-Flash addresses this with a joint schema head. Its request is a state plus a schema of questions, not just a single candidate list. Its backbone still runs once, and its outputs are still probabilities over allowed options. What changes is how the head extracts and combines the evidence.

This section follows the local joint_schema_model.py, joint_head_config.json, and config.json, distributed with the Clef-Flash release. We will use \(i\) for a question, \(j\) for an option within that question, \(Q\) for the number of questions, and \(O=\sum_i K_i\) for the total number of options. Backbone vectors have width \(d=4096\); the head projects most computation to \(D=1024\).

Qwen3.5 under the hood

The release uses Qwen3.5-9B. Its configured text stack has 32 layers: three linear-attention blocks followed by one full-attention block, repeated eight times. That is a hybrid causal backbone, not the generic full-attention transformer drawn in Part I. We still take its final hidden states rather than generate an answer.

Consistent order is not structural equivariance. Unlike Part I’s structural equivariance construction, this implementation canonicalizes choice options by sorting their string IDs before packing. This removes variation from caller-supplied choice-key order, but does not eliminate the backbone’s underlying order sensitivity. Schema fields retain their supplied order, as do score levels, whose positions define their numeric meaning.

From comparing summaries to sharing evidence

In Part I, the backbone reads the whole input, but the head receives only a small set of summaries: one vector per candidate and one answer vector. Even the attention-refined version can only exchange information among those gathered vectors. Think of it as making a decision from a few notes after putting the original message away.

Clef-Flash keeps the notes and the token-level representations of the message and schema. An option can use its starting vector to ask which parts of that shared evidence matter to it. For the team question, Billing could draw on “charged twice,” while Account access could draw on “I can still log in.” These examples illustrate the information paths the architecture permits, not measured attention from a model run.

The head then changes scale: it builds one vector for each field—Team, Refund, and Urgency—and lets those fields exchange information while reading the same token evidence again. Instead of only asking “Which team fits?”, it can assess the team decision in the context of the refund and urgency questions. The routed option vectors are kept separately for final scoring. This is what makes the head joint: related questions interact before their options are scored, although the model still returns a separate probability distribution for each field and does not enforce logical consistency.

Both architectures read supplied input rather than generate an answer. The Cloudflare blog post calls Clef’s backbone evaluation a prefill-only Qwen pass: process the packed request once to obtain hidden states, with no subsequent answer-token generation loop. The extra work happens in the head—first options read token evidence, then fields interact and read that evidence again. The important difference from Part I is therefore what the head can access and what interacts inside it, not a return to text generation.

Requests can also include images or videos. Qwen’s vision encoder supplies features at media-placeholder positions in the text stream. The decision head then works over the resulting hidden states in the same way. Text-only requests bypass vision processing.

Input packing in the implementation

The encoder builds a system prompt, a STATE: region, SCHEMA FIELDS:, and a fixed assistant suffix ending in JOINT SCHEMA DECISIONS:. Each field includes its ID, type, instructions, and allowed options. An option span covers serialized option ID and description text; an instruction span covers instruction text only.

The default encoder budget is 16,384 tokens. It truncates state text to fit while retaining the fixed schema and suffix; oversized fixed content raises an error. This is a request-encoding limit, not the backbone’s maximum positional capacity. Records are right-padded for a batched backbone pass, then processed individually by the head.

06 / Keep the evidence

Build pooled vectors and token memory

Clef-Flash first applies a learned LayerNorm to the backbone hidden states and removes each record’s padding. Call the resulting sequence \(\widehat{H}\in\mathbb{R}^{N\times d}\). Instead of gathering only the final token of each candidate, the head averages over the recorded spans:

\[\begin{aligned} q_i &= \operatorname{mean}_{n\in I_i}\widehat{H}_n \\ c_{ij} &= \operatorname{mean}_{n\in S_{ij}}\widehat{H}_n \\ g &= \widehat{H}_{N-1} \end{aligned}\]

Here \(I_i\) is question i’s instruction span and \(S_{ij}\) is its option j’s span. Thus \(q_i\) represents the question, \(c_{ij}\) represents the option in context, and g is the global suffix state. All three remain 4,096-wide. Mean pooling is a different readout choice from endpoint gathering, not a claim that pooling removes the backbone’s order dependence.

For example:
\(i\): the Team question.
\(j\): its Billing option.
\(S_{ij}\): the positions of the tokens encoding that option’s serialized ID and description.

In parallel, every unpadded token is projected into a shared memory:

\[M=\widehat{H}W_{\mathrm{memory}}^\top\in\mathbb{R}^{N\times D}\]

The memory contains the whole encoded request: state tokens, instructions, option descriptions, formatting, and suffix. It is not a separate database or an external retrieval index. The head will use M as keys and values in cross-attention. The pooled vectors provide starting points; memory keeps more detailed contextual evidence available.

A second view of each option: lexical content

For each option, the code also looks up its token IDs in the backbone’s output-embedding matrix \(E_{\mathrm{out}}\) and averages those rows:

\[\ell_{ij}=\frac{1}{|S_{ij}|}\sum_{n\in S_{ij}} E_{\mathrm{out}}[x_n]\in\mathbb{R}^{d}\]

The contextual vector \(c_{ij}\) depends on the option’s position and preceding text. The lexical vector \(\ell_{ij}\) instead comes from a parameter-table lookup of the serialized option tokens. For a fixed option token sequence and fixed model weights, it does not depend on the surrounding request. Because the span contains the option ID and description, it reflects both—not just a clean natural-language team name.

The language-model output weights are reused, not used to generate. Clef-Flash skips next-token vocabulary-logit computation, but still reads rows of the output-embedding matrix. The release config does not tie this matrix to the input embedding table. A lexical vector is a feature representation, not a vocabulary probability.

07 / Let each option read the state

Turn an option into an evidence query

A pooled Billing vector is not yet an explicit representation of why Billing fits this request. The head therefore combines three projected signals: the option in context, its lexical content, and the question it belongs to. Using column-vector notation for individual vectors:

\[r^{(0)}_{ij}=W_{\mathrm{context}}c_{ij}+W_{\mathrm{lexical}}\ell_{ij}+W_{\mathrm{oq}}q_i\in\mathbb{R}^{D}\]

These are three distinct, bias-free projections from 4,096 to 1,024 dimensions. The question term matters: the same option wording can play different roles under different instructions. The queries for all O options are concatenated into a short sequence R.

Each of the two EvidenceRoutingLayer blocks applies pre-normalized cross-attention and a residual feedforward update:

\[\begin{aligned} R' &= R+\operatorname{MHA}(\operatorname{LN}(R),\operatorname{LN}(M),\operatorname{LN}(M)) \\ R'' &= R'+\operatorname{FFN}(\operatorname{LN}(R')) \end{aligned}\]

The query rows are options; the key and value rows are tokens. In our example, the Billing query could draw on “charged twice,” while Account access could draw on “I can still log in.” These are explanations of what the attention operation permits, not verified descriptions of what a particular model run attends to.

Importantly, these routing layers do not self-attend across options. Concatenating all queries makes the operation convenient to compute together, but each query reads the shared token memory. This differs from Part I’s refinement layer, which directly mixed the selected candidate and answer rows.

The release uses 16 attention heads and a feedforward network \(1024\rightarrow4096\rightarrow1024\), with GELU. After both layers, the O routed vectors are split back into their question-specific option lists. We will call those final vectors \(r_{ij}\), keeping them available for scoring later.

Source: EvidenceRoutingLayer and option-query construction, lines 242–278 and 388–403; head configuration.

08 / Let related decisions interact

One field vector for each question

The next stage changes the unit of computation. Instead of refining every option together with an answer vector, Clef-Flash constructs one vector for each field—its name for a question in the schema. This vector starts with the question and a weighted summary of that question’s routed options.

\[\begin{aligned} b_i &= W_{\mathrm{question}}q_i \\ \alpha_{ij} &= \operatorname{softmax}_{j}\!\left(\frac{r_{ij}^{\top}b_i}{\sqrt{D}}\right) \\ z_i &= \sum_{j=1}^{K_i}\alpha_{ij}r_{ij} \\ f_i^{(0)} &= b_i+\operatorname{LN}(z_i)+W_{\mathrm{global}}g+e_{\mathrm{type}(i)} \end{aligned}\]

The question projection \(W_{\mathrm{question}}\) is separate from the projection used in option queries. The type embedding marks whether the field is noul, choice, or score. The same global suffix representation contributes to every field, while the question and option summary make each field distinct.

Summary weights are not answer probabilities. The \(\alpha_{ij}\) values determine how to construct a field’s starting representation. They are an internal pooling operation. Final option probabilities are computed later, after field decoding and scoring.

The Q field vectors then pass through four pre-normalized transformer decoder layers. Each layer has field-to-field self-attention, field-to-token cross-attention, and a feedforward network, with residual connections around each sublayer. The cross-attention reads the same M used during option routing.

The team field can now use information represented in the refund field, and vice versa. The architecture permits that interaction; it does not hard-code a rule such as “refund implies Billing,” nor ensure that all outputs will be logically consistent.

After four layers, a final field LayerNorm produces \(f_i\in\mathbb{R}^{D}\). The routed options do not enter these decoder layers as rows. They remain separate, ready to be paired with their own decoded field.

What “joint” means here

Questions share evidence and interact through their representations. The model still returns a separate probability distribution for each field—not an explicit joint distribution over every combination of answers.

Source: field construction and decoding, lines 405–424. Four decoder layers, 16 heads, and a 4,096-wide feedforward network are set by joint_head_config.json.

09 / Compare, combine, and return

Two scoring paths, one logit per option

We have reached the same conceptual point as Part I: turn representations into option scores. But Clef-Flash does not use a shared bilinear matrix here. It combines a lexical similarity prior with a learned joint score, gated by a learned scalar.

At this point, the head has a refined decision context for each field, an evidence-enriched vector for each possible answer, and a lexical vector representing each option’s token content. It now assesses every option in two complementary ways: a more direct comparison using its wording, and an evidence-conditioned comparison using the refined field and option vectors.

The prior bypasses the head’s attention layers

For Billing, this branch asks:

“How compatible is this option’s wording with the question and overall request?”

It compares the lexical Billing vector with the original question vector plus the global request vector, without passing through the head’s attention layers. This is not just keyword matching: the lexical embeddings are learned, and the question and global vectors already contain context from Qwen.

The prior compares the lexical option vector with the sum of the original question vector and global suffix vector:

\[\operatorname{prior}_{ij}=\tau_{\mathrm{prior}}\,\cos(\ell_{ij},q_i+g)\]

This computation stays at width 4,096. It bypasses option routing and field decoding, although its question and global inputs still come from the contextualized backbone. “Prior” is the implementation’s name for an additive score branch; it is not a separately normalized Bayesian prior.

The joint score compares a field with each routed option

This branch asks a richer question:

“Given the evidence gathered for Billing and the refined context of the Team decision, how well does Billing fit?”

It pairs the Team field, after it has interacted with Refund and Urgency and reread token evidence, with the Billing option, after its evidence-routing updates.

First normalize the routed option with a learned LayerNorm, \(u_{ij}=\operatorname{LN}(r_{ij})\). Then construct a feature vector that describes both representations and their relationship:

\[\begin{aligned} v_{ij} &= [f_i;u_{ij};f_i\odot u_{ij};|f_i-u_{ij}|] \\ v_{ij} &\in\mathbb{R}^{4D} \\ \operatorname{joint}_{ij} &= \tau_{\mathrm{joint}}\,\cos(f_i,u_{ij})+\operatorname{MLP}(v_{ij}) \end{aligned}\]

The concatenation includes the field, the option, their elementwise product, and their absolute difference. A shared MLP maps \(4096\rightarrow1024\rightarrow1\), with GELU between its two linear layers. It can learn a nonlinear compatibility correction alongside the scaled cosine term. Neither the MLP nor the cosine scale has a separate parameter set for Billing or any other candidate ID.

In simple terms, cosine similarity measures how aligned the two vectors are. The MLP—a small learned neural network—adds a more flexible compatibility assessment, using both vectors and their products and differences. The same machinery scores Billing, Technical support, and every other supplied option; there is no dedicated Billing output neuron.

Clef adds the lexical-prior score to a scaled version of the joint score. A learned gate controls how much the joint branch contributes. The result is one final score per option, called a logit; it is not yet a probability. The branches combine as:

\[\begin{aligned} L_{ij} &= \operatorname{prior}_{ij}+\sigma(\gamma)\operatorname{joint}_{ij} \\ p_{ij} &= \frac{\exp(L_{ij})}{\sum_{k=1}^{K_i}\exp(L_{ik})} \end{aligned}\]

The gate \(\gamma\) and both log scales are shared learned scalars. In the code, each cosine scale is \(\tau=\exp(\min(\eta,\log 100))\), so its maximum is 100. The sigmoid gate lies between zero and one; it is not a request-specific routing decision or a normalized mixture weight for the two branches.

Softmax runs within each question’s own options, not across all O options in the request. The Billing option competes with the other teams, not with the refund field’s True option. The head returns variable-length logit tensors for each field, so it does not allocate a fixed 255-option output bank. Padded backbone tokens have already been removed from memory.

Think of this as three separate competitions: Billing versus the other teams; True versus False; and Routine versus Soon versus Immediate. Softmax converts the scores in each competition into probabilities that sum to one. The fields have shared information upstream, but their options do not compete across field boundaries.

Three answer types share the same probability machinery

The API converts each field’s distribution into its requested type:

  • choice: return the highest-probability option ID, its winning probability as confidence, and the option probabilities.
  • noul: score the two allowed options, True and False, then return \(P(\mathrm{true})\). Despite the name, this is a boolean/proposition readout—not a “null” or abstention mode.
  • score: enumerate the supplied levels from zero and return their expected index, \(\sum_j j\,p_{ij}\), along with the probabilities and legend. Its reported confidence is the maximum option probability, not a confidence interval for the expectation.

For example, an illustrative urgency distribution of 60% Routine, 30% Soon, and 10% Immediate—[0.6, 0.3, 0.1] over levels 0, 1, and 2—would return a score of 0.5, not just the winning level 0. It is the average level index weighted by the probabilities. This number inherits the meaning and spacing of the application’s level definitions; the head itself still predicts a categorical distribution.

No answer tokens are decoded. systemone() maps option IDs back to each question, rounds returned numeric values to four decimals, and reports output_tokens: 0. The transformer decoder inside the head performs representation refinement, not an autoregressive generation loop.

Source: scoring, typed readout, and systemone(), lines 426–457 and 523–576.

What carries over from the simple blueprint?

Clef-Flash still makes request-defined decisions from a pretrained backbone. Shared comparison functions allow option counts to vary. But the readout is no longer just “gather, optionally self-attend, then apply a bilinear matrix.” It is pool, route evidence, construct fields, decode them jointly, and combine two scoring paths.

The caveats from Part I still apply. The packed backbone can introduce option and field order effects. Field interaction does not enforce logical constraints between answers. Softmax and the API’s confidence fields do not establish calibration. And a choice field cannot select an option missing from its criteria; boolean noul is not an automatic escape hatch.

The local code establishes the release’s inference architecture, not its training recipe. Cloudflare’s original blog article adds a separate account of post-training, described next; it does not provide loss weights, full dataset details, or enough information to reproduce the optimization.

The progression

The first blueprint compares representations. Clef-Flash makes those comparisons evidence-conditioned and schema-aware: each option reads the request, then each field reads both the evidence and the other fields.

For the full tensor flow, including vision internals and every projection, see the complete Clef-Flash architecture map. The crucial distinction is already visible here: we have changed the readout’s access to evidence, not returned to generating answer text.

10 / Post-train for calibrated decisions

Train the decision, not a text continuation

Cloudflare describes adapting a frozen Qwen base with a learned routing head and low-rank adapters, then optimizing both answer accuracy and the quality of the reported probabilities.

This section summarizes Cloudflare’s original article, “How we trained Clef”, rather than a training implementation in the repository. The article names Qwen3.5-9B for Clef-Flash, matching the local model card and release configuration. The larger Clef uses Qwen3.8-27B.

Frozen base weights do not mean fixed representations

According to the excerpt, the base Qwen weights remain frozen while the routing head and rank-256 low-rank adapters are jointly optimized. Adapters add trainable updates inside the backbone, so its resulting representations can still adapt to decision tasks without updating the original base weights. This differs from the head-only frozen-backbone baseline in Part I.

Supervised choice learning

Label-smoothed cross-entropy

The reported objective trains over valid schema outputs, with softened targets rather than placing all target mass on one choice. This discourages excessively sharp predictions during training; the excerpt does not specify the smoothing amount or its allocation.

Probability quality

Brier loss

A Brier loss penalizes squared differences between predicted probabilities and target outcomes. It complements cross-entropy by directly evaluating the probability vector. Cloudflare describes using it to refine calibration; adding the loss does not by itself prove that deployed confidence is calibrated.

For our routing example, choosing Billing correctly is one goal. Another is making the reported probability informative: among comparable requests assigned about 80% confidence, roughly 80% should be correct. Calibration must be measured on held-out data, including the intended deployment conditions.

Vary the schema during training

The excerpt reports internal synthetic datasets that vary field order, prompts, and schema structure. This exposes the model to different presentations of related decisions. It is training-time robustness, not a structural equivariance guarantee: shuffled data can reduce order sensitivity without eliminating it. The architectural conditions and hybrid-backbone caveats in Part I’s choice-order section still apply, and ordered score levels must retain their meaning.

RLCD adds ordinal and whole-record incentives

Cloudflare also reports Reinforcement Learning for Calibrated Decisions (RLCD) as a secondary optimization target:

  • Adjacent ordinal choices receive partial credit. For an urgency scale, a neighboring level can be treated differently from a distant error. This uses meaningful scale order, not arbitrary candidate-list position.
  • Fully precise records receive a reward. The objective considers getting the complete set of field outputs right, rather than only evaluating each field separately.
  • A reference penalty limits distribution shift. The excerpt describes discouraging excessive departure from a reference distribution, but does not specify the penalty’s exact form.
Architecture and optimization work together

The head determines where decisions come from. Post-training teaches which decisions to prefer, how probabilities should behave, and how ordinal and whole-record errors should be valued. None of these objectives guarantees logical consistency or calibration on its own.
